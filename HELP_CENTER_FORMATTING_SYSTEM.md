# eBanano Help Center — система форматирования и визуальной иерархии

**Статус:** рабочий стандарт для русского Help Center  
**Дата:** 2026-09-18

## Зачем это нужно

Хорошая статья не должна требовать чтения сверху вниз.

Большинство людей приходят в Help Center с конкретной задачей и сначала **сканируют страницу глазами**:
- подходит ли эта статья;
- где мой случай;
- что делать прямо сейчас;
- что можно не читать;
- где следующий шаг.

Поэтому форматирование — это не украшение текста. Оно должно сокращать время до нужного ответа.

## Правило первых секунд

В первом экране страницы человек должен понять минимум две вещи:

1. он попал в нужную статью или нет;
2. что здесь делать дальше.

Не начинать страницу с:
- длинного определения;
- списка исключений;
- истории функции;
- нескольких одинаково важных callout-блоков.

Хороший первый экран:
- короткая живая подводка;
- одно главное действие или развилка;
- при необходимости один действительно важный риск.

## Как человек читает статью

Проектируем страницу в три слоя.

### Слой 1 — сканирование

Человек видит:
- заголовок;
- первые 1–2 предложения;
- названия секций;
- карточки, вкладки или заголовки аккордеонов;
- предупреждения.

Этого должно хватать, чтобы найти нужный кусок без чтения всей статьи.

### Слой 2 — действие

Когда нужный блок найден, человек получает:
- короткие шаги;
- точные UI-названия;
- одну последовательность действий;
- понятный критерий «получилось / не получилось».

### Слой 3 — детали

Только после этого:
- объяснение причин;
- редкие случаи;
- технические детали;
- альтернативные варианты.

Для этого используем progressive disclosure: Accordion, Tabs и дополнительные блоки.

## Компонент выбирается по вопросу пользователя

| Что человек хочет понять | Используем | Почему |
| --- | --- | --- |
| **Что делать по шагам?** | `Steps` | Хорошо считывается последовательность |
| **У меня iPhone или Android — куда нажимать?** | `Tabs` | Человек сразу отсекает ненужную платформу |
| **Какой из этих случаев мой?** | `AccordionGroup` | Заголовки становятся быстрым меню по симптомам |
| **Чем отличаются варианты?** | Таблица | Сравнение видно без чтения нескольких абзацев |
| **Куда перейти дальше?** | `Card` / `Columns` | Визуально отделяет следующий сценарий |
| **Какой статус у функции?** | `Badge` | Короткий статус не превращается в отдельный абзац |
| **Что важно знать?** | `Info` | Выделяет факт или условие |
| **Есть полезный необязательный совет?** | `Tip` | Не мешает основному сценарию |
| **Действие может создать проблему?** | `Warning` | Риск нельзя пропустить при сканировании |
| **Действие необратимо / опасно для денег или доступа?** | `Danger` | Использовать редко, только для реального серьёзного риска |
| **Всё получилось?** | `Check` | Даёт явную точку завершения |
| **Нужно показать экран приложения?** | `Frame` + изображение | Скриншот становится частью инструкции, а не декором |
| **Есть развилка процесса, которую сложно объяснить текстом?** | Mermaid | Только когда схема реально быстрее текста |
| **Нужна дополнительная расшифровка термина?** | `Tooltip` | Только для необязательного контекста |
| **Нужна иерархия статей?** | Вложенные navigation groups | Это правильное дерево страниц в Mintlify |

## Что НЕ использовать ради разнообразия

### Tree

Публичный Mintlify `Tree` предназначен прежде всего для иерархических структур вроде файлов и папок.

Не использовать его как декоративную замену:
- навигации;
- Steps;
- decision tree.

Для дерева страниц использовать вложенные группы в `docs.json`.

### Mermaid

Не рисовать схему для четырёх линейных шагов.

Mermaid нужен, если у пользователя есть настоящая развилка:
- есть сеть / нет сети;
- профиль установлен / не установлен;
- платёж завершён / обрабатывается / отклонён.

Если AccordionGroup или Steps читаются быстрее — схема не нужна.

### Tooltips

Не прятать туда обязательную информацию.

На мобильном и при быстром сканировании пользователь может не открыть подсказку. Tooltip — только для дополнительной расшифровки.

### Callouts

Не превращать страницу в разноцветную гирлянду.

На обычной странице желательно не больше 1–2 заметных callout-блоков одновременно в зоне чтения.

## Правила сканирования

### Заголовки

Заголовок должен позволять понять содержание блока без чтения текста под ним.

Хорошо:
- «Сеть есть, а интернета нет»
- «QR-код на этом же телефоне»
- «Деньги списались дважды»

Плохо:
- «Дополнительная информация»
- «Важные моменты»
- «Особенности»

### Абзацы

- 1–3 предложения.
- Одна мысль на абзац.
- После большого интерактивного блока — визуальная пауза и новый смысловой заголовок.

### Списки

Использовать, когда элементы действительно однотипны.

Если список превращается в 8–10 длинных пунктов, его нужно:
- разделить;
- свернуть;
- превратить в таблицу;
- или дать отдельные подзаголовки.

### Таблицы

Для consumer Help Center:
- желательно 2–3 столбца;
- первая колонка должна позволять быстро найти свой вариант;
- не класть длинные инструкции внутрь таблиц.

### Tabs

Использовать, когда задача одна и та же, меняется только платформа или вариант.

Все вкладки должны иметь одинаковую структуру. Пользователь не должен гадать, почему на iPhone четыре шага, а на Android внутри той же задачи внезапно другая статья.

### Accordions

Название аккордеона должно быть достаточно информативным, чтобы человек понял: открывать его или нет.

Хорошо:
> Сеть есть, а интернета нет

Плохо:
> Вариант 2

Критическое предупреждение не прячется внутрь закрытого аккордеона, если оно относится ко всей странице.

### Cards

Карточки нужны для выбора направления, а не для оформления каждого абзаца.

Не показывать 8–10 одинаковых карточек без группировки — глаз перестаёт понимать, что важнее.

## Визуальный ритм статьи

Не должно быть единого шаблона «текст → Steps → Warning → Card».

У каждой статьи композиция зависит от задачи.

### Тип A — маршрутизатор

Пример: главная.

Структура:
- короткая подводка;
- 3–4 смысловых группы по этапу пути;
- внутри группы 2–3 Card;
- второстепенное ниже.

### Тип B — выбор / решение

Пример: выбор пакета.

Структура:
- короткое правило;
- визуальная карта критериев;
- сравнение;
- детали по каждому критерию;
- редкие вопросы в AccordionGroup.

### Тип C — процедура

Пример: установка.

Структура:
- checklist перед началом;
- Tabs по устройствам;
- Steps внутри вкладки;
- альтернативные способы в AccordionGroup;
- Check с результатом.

### Тип D — troubleshooting

Пример: интернет не работает.

Структура:
- один глобальный Warning, если нужен;
- AccordionGroup по наблюдаемым симптомам;
- внутри каждого — только проверки для этого симптома;
- support escalation в конце.

### Тип E — состояние / управление

Пример: остаток и пополнение.

Структура:
- 2–3 визуальных блока «что здесь можно увидеть»;
- основной action flow;
- редкие объяснения в Accordion;
- Badge для статуса незапущенной функции.

### Тип F — политика / деньги

Пример: возврат.

Структура:
- короткий ответ;
- условия;
- сценарии;
- реальный Warning/Danger при риске;
- один путь запроса.

## Скриншоты и Frame

Скриншот добавляется только если он отвечает на вопрос:

> «Что именно я должен увидеть или нажать?»

Не добавлять изображения:
- только потому что в Figma красивый экран;
- если UI ещё нестабилен;
- если текст и без изображения быстрее.

Когда интерфейс стабилизируется:
- оборачивать скриншоты в `Frame`;
- писать нормальный alt;
- caption использовать только если он реально поясняет, что смотреть на изображении.

## Навигационное дерево

Для русской базы использовать не более двух уровней смысловой вложенности под корнем.

Группировать по жизненному циклу:
- до поездки;
- покупка и заказ;
- установка и подключение;
- во время и после поездки;
- аккаунт и программы;
- помощь.

Ошибки должны жить рядом с действием, которое могло не получиться, а не в отдельной огромной папке «Troubleshooting».

## Доступность

Интерактивный компонент не заменяет понятный текст.

- изображения получают alt;
- названия Accordion понятны без открытия;
- Tabs не содержат критическую информацию только в одной платформе;
- цвет не является единственным сигналом статуса;
- Warning/Danger используются по смыслу.

## Главное правило

Если компонент не помогает человеку **быстрее найти, понять или выполнить действие**, его не нужно добавлять.

Разнообразие страницы — следствие разных пользовательских задач, а не цель само по себе.
