# eBanano — Purchase flow → Help Center mapping

## 0. Как использовать Figma

Figma в этом документе показывает только концепцию сценария и последовательность экранов.

Нельзя брать из макетов как факты:
- цены;
- страны и покрытие;
- объёмы трафика;
- правила активации;
- условия возврата;
- тексты про автопродление;
- бонусные и реферальные правила;
- любые сроки или ограничения.

Все такие данные подтверждаются отдельно по продуктовым решениям, документации поставщика, production API и юридическим документам.

**Статус:** UX baseline  
**Дата:** 2026-09-18  
**Основание:** актуальные макеты purchase/order flow.

## 1. Текущий пользовательский путь

По макетам пользователь проходит:

1. Страница направления.
2. Проверка совместимости устройства.
3. Выбор группы пакетов: «Безлимит» / «Стандарт».
4. Выбор конкретного пакета.
5. Раскрытие «О пакете» у выбранного варианта.
6. Переход к оформлению заказа.
7. Проверка coverage / traffic / validity / price.
8. Промокод.
9. Bananos.
10. Автопродление.
11. Подтверждение и оплата.
12. Страница заказа.
13. Квитанция / возврат / состояние автопродления.
14. «Установить или поделиться».
15. Установка на своё устройство либо передача QR другому человеку.

Help Center не должен создавать отдельную статью на каждый экран этого flow.

# 2. Что интерфейс уже объясняет сам

Не нужно дублировать в Help Center:

- где переключить «Безлимит / Стандарт»;
- как выбрать строку пакета;
- где находится кнопка «Выбрать»;
- где вводится промокод;
- где находится toggle Bananos;
- где находится toggle автопродления;
- состав summary выбранного заказа, если подписи очевидны;
- наличие кнопки «Установить или поделиться».

Help Center нужен для смысла и последствий, а не для пересказа интерфейса.

# 3. Где Help Center действительно нужен

## До выбора пакета

Пользователь может не понимать:

- чем standard отличается от unlimited;
- что означает дневной лимит;
- что происходит после лимита;
- когда начинается validity;
- какие страны входят в coverage;
- почему пакет может поддерживать 5G, но 5G не гарантирован в любой точке.

Canonical owner: статья №3 «Как выбрать тариф».

## «О пакете»

Это canonical product explanation конкретного offer.

Подробная модель: HELP_CENTER_PACKAGE_DETAILS_MODEL.md.

## Checkout

Пользователь может не понимать:

- что именно произойдёт при включении автопродления;
- когда будет следующее списание;
- какой пакет будет куплен;
- можно ли отключить;
- что произойдёт, если пакет исчезнет;
- как Bananos влияют на итоговую сумму;
- что такое цена будущего renewal.

Canonical owners:
- checkout/payment basics → №5;
- Bananos → №18 после redesign;
- renewal/top-up → №14.

## После покупки

Страница заказа является точкой входа в три отдельных сценария:

### Установить себе

→ статья №9.

### Передать другому человеку

→ post-purchase section статьи №6 + installation article №9 для устройства получателя.

Ключевое правило:
**покупатель не устанавливает профиль на своё устройство, если eSIM предназначена другому человеку.**

### Запросить возврат

→ статья №8.

Кнопка «Запросить возврат средств» не должна создавать впечатление гарантированного возврата. UI должен вести в request/review flow, где применяются eligibility rules.

# 4. Изменение границы статей

## Статья №5

Остаётся:
**Как оформить и оплатить заказ**

Она объясняет:
- order summary;
- payment;
- currency;
- promo;
- Bananos только как checkout option;
- toggle auto-renew только как решение, которое пользователь принимает перед оплатой.

Она НЕ объясняет всю механику renewal.

## Статья №6

Уточнить название/роль:

**Где найти заказ, eSIM и как передать её другому человеку**

Она становится canonical owner post-purchase действий:
- найти заказ;
- получить installation data;
- посмотреть receipt;
- выбрать «Установить или поделиться»;
- безопасно передать eSIM получателю;
- не установить gift eSIM на устройство покупателя.

## Статья №14

Переименовать:

**Остаток трафика, пополнение и автопродление**

Это лучше соответствует реальному продукту, чем старое «Остаток интернета, срок действия и окончание пакета».

Canonical scope:
- current balance;
- validity;
- обновлено;
- manual top-up;
- available top-up catalog;
- auto-renew enable/disable;
- выбранный renewal package;
- trigger <10%;
- future renewal price;
- paused state;
- package unavailable;
- failed charge;
- package exhaustion.

Это позволяет НЕ создавать отдельную статью «Как работает автопродление» и не раздувать Help Center.

В приложении ссылка «Как работает автопродление» может вести сразу на anchor внутри статьи №14.

# 5. UX-наблюдения по текущим макетам

## 5.1 «О пакете» внутри выбранной строки — хороший паттерн

Пользователь может быстро сравнить пакеты и раскрыть подробности только нужного.

Важно:
- не перегружать collapsed row;
- критичные ограничения нельзя прятать только в sheet, если они меняют смысл слова «Безлимит» или момент начала срока.

Например FUP должен быть виден уже у выбранного unlimited package.

## 5.2 Checkout правильно повторяет ключевые условия

Coverage / Traffic / Term / Price полезно повторить перед оплатой.

Это не считается вредным дублированием: здесь информация выполняет функцию **confirmation before purchase**, а не справки.

## 5.3 Автопродление

Экран в Figma показывает только концепцию будущей функции.

**Статус бизнес-логики: в разработке.**

До отдельного обсуждения не фиксируем в Help Center:
- момент автоматического продления;
- повторно покупаемый пакет;
- будущую цену;
- правила списания;
- поведение при недоступности пакета;
- поведение при неуспешной оплате;
- уведомления.

После утверждения логики checkout должен будет явно показывать все существенные условия до включения функции.

## 5.4 «Установить или поделиться» — правильная развилка

Она решает проблему gift flow лучше, чем отдельная покупка «на другого пользователя».

После покупки нужно явно дать два действия:

- **Установить на это устройство**
- **Передать для установки на другое устройство**

И предупредить, что установленную eSIM потом нельзя просто перенести.

## 5.5 Возврат со страницы заказа

«Запросить возврат средств» — правильная формулировка.

Не использовать «Вернуть деньги», если действие лишь создаёт запрос на review.

# 6. Открытые продуктовые вопросы, которые выявил макет

## Auto-renew и тип top-up

Правило <10% логично для data top-up.

Нужно отдельно решить поведение для продуктов, у которых provider top-up mode = validity_period:

- разрешаем ли auto-renew;
- какой trigger использовать;
- remaining validity вместо remaining traffic;
- или auto-renew v1 доступен только для data top-up compatible packages.

До решения нельзя использовать одно правило «<10% трафика» для всех top-up capable offers.

## Auto-renew и цена

Если цена того же top-up package изменилась между включением и будущим renewal:

- списываем новую цену автоматически;
- просим повторное согласие;
- ставим renewal на pause при изменении цены.

Это нужно решить до реализации recurring payments.

## Недоступный пакет

Уже принято:
- не выбирать replacement автоматически;
- pause renewal;
- notification;
- пользователь выбирает новый пакет сам.

## Failed charge

Нужно определить:
- сколько retry attempts;
- есть ли retry вообще;
- когда auto-renew становится paused;
- какое уведомление получает пользователь.

# 7. Help Center principle confirmed by the flow

Интерфейс отвечает на вопрос **«где нажать?»**.

Help Center отвечает на:
- **«что это означает?»**
- **«что произойдёт после этого?»**
- **«что делать, если результат другой?»**
- **«какие ограничения я должен знать до подтверждения?»**

Если статья начинает пошагово пересказывать очевидный экран purchase flow, она лишняя или слишком подробная.
